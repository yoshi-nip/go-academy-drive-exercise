# 開発・レビューで確認すること

更新：2026-10-23。[実装方針](実装方針.md)を仕様の基準とする。未確定のAPI細部は、各実装で決めた内容を先に示してレビューする。

## レビュー依頼に添える情報

- 今回実装した機能と対象ファイル。
- 決めた仕様、迷っている点、設計理由。
- 実行したコマンド・リクエストと結果。
- テスト済みの範囲、まだ確認していない範囲。

## データの意味とID

- API・外部キーはusers.id、元データ照合はsource_user_idを使用しているか。
- IDの連続性を仮定していないか。AUTO_INCREMENTの欠番は正常。
- 紹介対象は視聴テーブルに存在するユーザーか。将来残る古いusersまで無条件に紹介していないか。
- 視聴反応を「好き」「完走」、視聴記録なしを「確実に未視聴」と説明していないか。
- 推薦候補の元データに存在しないスコアやランキングを仮定していないか。
- 推定年代・性別を今回の候補優先に使っていないか。

## 紹介・作品表示

- 共通作品→共通ジャンル→その他の優先順を守り、同じ相手を重複して返さないか。
- 自分を除外し、最大10人、不足時の下位区分からの補充が動くか。
- 空・不明のジャンル同士を共通点としていないか。
- 同区分内のランダム抽出を適切に検証しているか。「毎回必ず違う結果」をテスト条件にしていないか。
- 相手の視聴作品は最大5作品・ID順、相手への推薦候補は最大5作品・ランダムか。
- 推薦候補は相手本人の視聴記録を除外しているか。閲覧者の視聴記録の除外は未採用の仕様として区別しているか。
- 候補0件・共通点なしを正常な結果として扱えているか。

## Go・HTTP・DB

- handlerがHTTP、serviceが業務ルール、repositoryがDBアクセスを担っているか。小さい実装に対して過剰に分割していないか。
- ログインなしのuserID指定を本人認証と混同していないか。
- 不正な入力・不存在ID・DB失敗を、決めたステータスとJSON形式で返せるか。
- SQLの値をパラメータで渡し、rows/接続の後処理やエラーを扱っているか。
- context・タイムアウトをDB処理へ渡せるか。
- Ping失敗時にも作成済みのsql.DBを閉じ、成功時は呼び出し元で寿命を管理しているか。
- 設定ファイルの場所・環境変数名が実装と一致するか。Pingだけでなく、目的のDB・テーブルを参照できるか。
- 接続テストは失敗時に停止し、nilのDBをCloseしていないか。
- 通常参照はReplica、更新はPrimaryか。更新直後の最新性が必要な読み取り先を考慮しているか。
- 元ログ全件をAPIのたびに集計していないか。N+1や大きい集合のランダムソートは実測できているか。
- interfaceの役割を説明でき、2方式の差し替えに意味があるか。
- 認証情報をソース・レスポンス・ログに出していないか。

## データ加工を変更する場合

- 元テーブルを変更せず、必須値・長さ・マスタ対応を反映前に検証しているか。
- 再投入でusers.idとsource_user_idの対応を維持するか。
- 視聴と推薦の交差が0件か。件数の単位が行なのかユーザー×作品の組なのか明確か。
- 関連テーブルの全件置き換えはトランザクション内で行い、途中失敗で戻るか。
- コミット前の失敗と、コミット後のReplica検証失敗を区別しているか。
- 再投入前のAPI・元データ更新停止、投入後のReplica確認を行うか。

## テストの優先例

- 共通作品あり／共通ジャンルのみ／共通点なし。
- 同じ作品を複数エピソードで観測したデータでも重複しない。
- 候補0人・10人未満・10人超過、自分自身の除外。
- 視聴・推薦0件、空ジャンル、存在しないID。
- DBの失敗・キャンセル・タイムアウト。
- interfaceの各方式が同じ契約を満たすこと。

毎回すべての項目をテストするのではなく、変更に関係する項目を選ぶ。HTTP異常系などはhttptest、業務ルールは小さい固定データ、SQLの結合・性能は実DBで確認する。

## 現在の実装に対する重点確認

- アプリ用userIDはuint64で受け渡し、SQL直前にintへ縮小していないか。作品ID・ジャンルIDは文字列のまま保持する。
- /users/:userID/watch-seriesは不正IDを400で拒否し、取得処理を呼ばないか。取得失敗は500、0件は空配列か。
- 不存在ユーザーと視聴0件は現状未区別。404対応が済んだと扱わない。
- 次のジャンル集計は表示用5作品ではなく全視聴シリーズを対象にし、再生回数・視聴時間と説明しない。
- テストはアシスタントが作成・更新する。handlerはスタブでHTTPと引数を、repositoryは実DBでSQLの結果を検証する。
