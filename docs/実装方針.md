# 実装方針（2026-10-23時点）

## 目的と進め方

視聴作品・ジャンルをきっかけに相手を紹介し、共通点や相手経由の作品発見を提供するGoのバックエンド演習。JSON APIで完結し、Web画面とログイン機能はMVPの対象外。

Goの基礎、struct/map/slice、interface、API、DB操作、テストを学ぶ。設計・アプリ本体のGo実装は本人が考え、テストの作成・更新はアシスタントが担当する。必要に応じてレビューする。本書を設計方針の正本とする。DDLと加工処理は実装済み。実装済みのAPIと未確定のAPI案を区別する。

## Goの構成方針

本人の方針として `handler → service → repository` を分ける。handlerはHTTP入出力、serviceは紹介ルールなどの業務処理、repositoryはDBアクセスを担当する。詳細なディレクトリ・型・interfaceは着手時に考え、学習しながら修正する。

現在はGinのHTTPサーバーとGET /healthが実装済み。ルーティング経由のHTTP 200・JSON応答をテスト済み。database/sqlとgo-sql-driver/mysqlによるReplica接続、godotenvによる設定読み込み、接続テストを実装済み。接続プールは最大10・待機5・寿命5分、起動時Pingは3秒。GET /demo-usersも実装済み。視聴作品取得のGET /users/:userID/watch-seriesも実装済み。ジャンル集計APIとmainのDI接続も実装・テスト済み。紹介APIは未実装で、DB接続の後処理等にレビュー指摘が残る。進捗は[開発手順](開発手順.md)で管理する。

## フェーズ1の機能

1. デモで基準となるユーザーを選ぶ。
2. 視聴反応のあるユーザーから自分を除外し、共通作品がある人、共通ジャンルがある人、それ以外の順で紹介する。
3. 同じ優先順位の中ではランダムに選ぶ。優先枠に人数が足りなければ次の順位から補う。
4. 紹介理由、相手の視聴作品・ジャンル、2人の共通点を返す。
5. 相手の視聴作品に加え、その人への既存の推薦候補も返す。

この優先順は共通の話題を見つけるためのルールであり、人間同士の相性や恋愛適合性の評価ではない。共通点がなくても紹介対象から一律に除外しない。複数カテゴリに該当する人は最上位の区分に一度だけ含める。

「紹介された候補」と「相互LIKEで成立したマッチング」は別概念。フェーズ1は紹介までとし、LIKE等はフェーズ2で扱う。

## データの利用

元データはsample_dbに維持し、アプリ用の加工データを別MySQLのapp_dbへ投入する。各リクエストで約385万行の元ログを集計する構成にはしない。加工はまず手動で再実行可能な方法から始める。

- 5月の学習用ログでwatch_flag=1のユーザー×シリーズを重複排除し、視聴記録として扱う。
- 推薦候補は元ログのユーザー×シリーズから作り、そのユーザーに視聴記録のある作品を除く。
- episode対象もitem_target_series_idでシリーズ単位へそろえる。
- 相手向けの候補が閲覧者にも合うとは断定しない。
- 視聴記録がないことは確実な未視聴を意味しない。視聴フラグの時間閾値・帰属期間も未確認。
- user_watch_5m_*の履歴特徴量は定義未確認のため、最初の加工では使わない。
- 元データの推薦スコア・生成アルゴリズムは確認できていない。出現回数や表示位置をおすすめ度に変換しない。

5月の視聴反応ユーザーは148,065人。そのうち142,968人（約96.6%）に、視聴記録を除いた既存推薦候補が残る。候補平均は0件のユーザーを含め6.77作品。候補0件なら空配列等で返す。

## テーブルと投入済みデータ

実際の定義は[DDL](../db/schema/001_create_tables.sql)、実行方法は[DB手順](../db/README.md)を参照。2026-10-22にPrimaryへ適用・投入し、Replicaへの反映も確認済み。

|テーブル|列・制約|投入件数|
|---|---|---:|
|users|id: BIGINT UNSIGNED連番主キー、source_user_id: VARCHAR(64) UNIQUE、est_age、est_gender|148,065|
|series|元作品id: VARCHAR(64)主キー、title、genre_id|296|
|user_watched_series|user_id・series_idの複合主キー|187,922|
|user_recommended_series|user_id・series_idの複合主キー|1,002,461|

- APIと関連テーブルではアプリ用users.idを使う。Goのアプリ用IDはuint64、作品IDとジャンルIDはstring。元IDは照合・再投入用にsource_user_idへ保持する。
- 推定年代・性別は元の値を保持するが、今回の候補優先には使わない。
- IDとジャンルコードはutf8mb4_0900_binで照合。大文字・小文字を区別しても今回の対象人数は変わらず、マスタとの不一致はなかった。
- 関連テーブルにはusers/seriesへの外部キーがあり、親の削除・ID更新はRESTRICT。
- 視聴テーブルに(series_id,user_id)、seriesに(genre_id,id)、推薦テーブルに外部キーを支える(series_id)の索引を用意。
- ジャンル空文字は保存するが共通ジャンル判定から除外する。その他の不明値を一律に共通点扱いしない。
- ジャンル別サマリーはまだ作成しない。実測後に必要なら追加する。

## 加工と再投入

[加工処理](../db/import/README.md)は実装・実データ投入済み。Python標準ライブラリとmysql CLIを使い、抽出結果を接続内の一時テーブルで検証してから反映する。

usersは元IDで照合し、既存のアプリ用IDを維持して属性更新・新規追加。seriesも元IDで更新・追加。視聴・推薦の関連テーブルはトランザクション内でDELETE/INSERTし、件数と両集合の交差0件を確認してコミットする。users/seriesを全削除したり、関連テーブルをTRUNCATEしたりしない。

元データとAPIの更新が止まった状態で手動実行する。コミット前の失敗はロールバック。コミット後のReplica待機失敗はPrimaryの成功を取り消さない。IDには欠番が生じ得る。

元データから消えたusers/seriesは自動削除しないため、紹介対象はusers全体ではなく、視聴テーブルに存在するユーザーとする。

[検証結果](../db/import/検証結果.md)：実データの投入・Replicaの同件数を確認。再実行時のID維持とロールバックは独立DBの少量データで検証済み。実データ全件の成功後の再投入は未実施。

## 件数と表示順の決定

|対象|方針|
|---|---|
|ユーザー候補|最大10人。共通作品→共通ジャンル→その他。同区分内はランダム、自分・重複は除外。不足分を下位区分で補う|
|相手の視聴作品|最大5作品、作品ID順|
|相手への推薦候補|最大5作品、候補内でランダム。本人の視聴記録を除外し、閲覧者の視聴記録はまだ除外しない|
|共通作品・ジャンル|一定の順序で返す。上限と並び順の詳細はAPI設計時に決める|

推薦候補0件や共通点なしも正常な結果として扱う。候補不足なら存在する分だけ返す。紹介履歴の保存や「毎回必ず異なる人」の保証は入れない。紹介候補のランダム抽出方式は未確定。デモユーザーではORDER BY RAND() LIMIT 5を採用済みだが、性能評価は未完了。

## APIの実装状況と案

|API（実装済み・案）|役割|
|---|---|
|GET /demo-users（実装済み）|usersからランダム最大5件のIDを返す。200: {"users":[{"user_id":123}]}、取得失敗: 500|
|GET /users/{userID}/watch-series（実装済み）|視聴作品をID順・最大5件。0件は200と空配列、不正IDは400、取得失敗は500。不存在と視聴0件は現状区別しない|
|GET /users/{userID}/candidates|共通点の優先順と区分内ランダムで候補・紹介理由を返す|
|GET /users/{userID}/viewing-profile|相手の視聴作品・ジャンル別集計を返す|
|GET /users/{userID}/connections/{otherUserID}|2人の共通点と相手経由の作品候補を返す|

userIDは認証された本人ではなく、デモで選択したユーザー。後から認証情報に基づく本人IDへ置き換えられるよう、処理に必要な基準ユーザーIDと取得元を区別する。APIでは連番のアプリ用users.idを使う。元IDの文字列はURLに使わない。/demo-usersとwatch-series以外の上記URLは未実装の案。現在の固定データではusers全員に視聴記録があることを確認し、デモ取得はEXISTSを省略。再投入で対象が変わった際は再検証する。

不存在ID、候補0件、共通点なし、件数上限、同一ユーザー指定への応答を考える。履歴にない作品を「好き」「未視聴」と断定しない。

## DBの読み書き分離

元データ用mysql-localは保持。Primaryへの加工・更新をReplicaに非同期複製する。MySQL内部のDB名はどちらもapp_db。

|用途|現在稼働中のコンテナ|受け渡しCompose版の名前|ホスト接続先|
|---|---|---|---|
|元データ|mysql-local|このComposeの管理外|127.0.0.1:3307 / sample_db|
|書き込み|app_primary_db|app_primary_db|127.0.0.1:3308 / app_db|
|読み取り|app_replica_db|app_replica_db|127.0.0.1:3309 / app_db|

2026-10-22にComposeをinfra/mysqlへ配置。既存プロジェクトgo-exercise-dbと専用ボリュームを維持して名前を統一した。環境整備時にルート.envのアプリ用パスワードにDB側を合わせ、管理用の認証情報はinfra/mysql/.envに分離。現在のGoは別途src/.envのREAD_DB_*を読むため、設定の配置・キー名の統一は残作業。[環境手順](../infra/mysql/README.md)を参照。

- 通常の参照API：Replicaのapp_reader。
- アプリの更新：Primaryのapp_writer。
- DDLや加工用の管理処理：Primaryの管理者（将来は専用権限を検討）。
- 更新直後の結果など最新性が必要な参照：Primaryを使用する方針。
- 元データの加工・移送は実装済みのdb/import/run.pyで行う。

これは運用構成を学ぶために採用する。現時点で負荷試験によってReplicaが必須と判明したわけではない。
