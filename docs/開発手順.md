## 決定済み・採用済みの事項

- ID方式、投入範囲、DDL、再投入方針、候補の優先順・表示件数は[実装方針](実装方針.md)のとおり。
- Gin、GET /health、ポート8080を採用済み。
- handler → service → repositoryの責務分担は決定済み。serviceと業務repositoryはこれから実装する。
- DB接続はdatabase/sqlとgo-sql-driver/mysql、設定読み込みはgodotenvとos.Getenvを採用済み。
- 現在の接続設定は最大接続10、最大待機5、接続寿命5分、起動時PingContextのタイムアウト3秒。性能測定に基づく最適値ではなく、現時点の実装値。
- 通常参照はReplica。Primary用のGo接続設定はコメントアウトで、まだ利用していない。

## DB接続の残作業と検証範囲

- Ping失敗時にConnectDB内でdb.Close()する。成功時はmainのdeferで閉じる。
- 接続テストはrequire.NoError等で接続失敗時に停止し、nilのDBをCloseしない。テスト内のlog.Fatalfはt.Fatal等に替える。
- Goはsrc/.envのREAD_DB_*、Compose・接続確認スクリプトはルート.envのDB_READ_* / DB_WRITE_* / DB_NAMEを使用中。設定が二重化している。統一するか、用途別に維持して対応関係を明記するかは残作業。現状の読み込み位置は[環境手順](../infra/mysql/README.md)を参照。
- 前回レビューでgo test -count=1 ./...とgo vet ./...は成功。ただし、その後READ_DB_*へのキー変更があり、変更後の再実行は今回のドキュメントレビューでは行っていない。
- 現行の接続テストはPingまで。DB_NAMEの旧不一致はsrc/.envとコードのREAD_DB_NAMEへの変更で解消しているが、SELECT DATABASE()とusersのSELECTで目的のDB・テーブルを参照できることを次に確認する。
- 空設定・不正ポートのテストはある。明示的な設定値検証、タイムアウト発生の検証は未実装。

## 次の課題：デモユーザー取得

まず上の接続残作業を片づけ、Replicaから実データをSELECTする。その後、デモユーザー取得APIへ進む。Goコードは本人が実装する。

1. usersとuser_watched_seriesから、視聴記録のあるアプリ用users.idを取得するrepositoryを作る。JOINによるユーザーの重複を避ける。
2. SQLには件数上限と順序を指定する。具体的な上限、JSONの公開項目、ページングは実装前に決める。
3. handlerへ接続し、候補のAPI案GET /demo-usersを確定させる。DBハンドルは起動時に作成したものを渡し、リクエストごとにConnectDBしない。
4. 正常系、0件、DB失敗を確認する。HTTPテストと実DBでのSELECT確認を区別して記録する。

完了条件：curlで実在するアプリ用ユーザーIDを件数制限付きのJSONとして取得できる。その後、指定ユーザーの視聴作品・ジャンル取得へ進む。

## まだ決めていないこと

- 業務APIの確定パスとJSON形式、エラーのHTTPステータス。不正ID・不存在ID・同一ユーザー指定の扱い。
- デモユーザー一覧と共通作品・ジャンルの上限、順序、ページング。
- 具体的な型・依存関係の渡し方と、2方式を差し替えるinterfaceの対象。責務分担の方針自体は決定済み。
- ランダム抽出のSQL方式。実データで計測して選ぶ。

未決事項は対象のAPIへ着手するときに決める。確定した内容は実装方針とリクエスト例へ反映する。

## 更新・レビューの進め方

- 小さい単位で実装し、対象となる行の状態と検証結果を更新する。
- 「コードを書いた」「ローカルで実行した」「実データで確認した」を分けて記録する。
- ルールを変更したら実装方針を更新し、変更理由も残す。
- 調査時点の数値・検証結果は履歴として残し、最新の状態と混同しない。
