## 決定済み・採用済みの事項

- ID方式、投入範囲、DDL、再投入方針、候補の優先順・表示件数は[実装方針](実装方針.md)のとおり。
- Gin、GET /health、ポート8080を採用済み。
- handler → service → repositoryの責務分担は決定済み。ユーザー取得repositoryは実装済み。単純取得はhandlerからrepositoryへ委譲し、serviceは業務ルールの追加時に導入する。
- DB接続はdatabase/sqlとgo-sql-driver/mysql、設定読み込みはgodotenvとos.Getenvを採用済み。
- 現在の接続設定は最大接続10、最大待機5、接続寿命5分、起動時PingContextのタイムアウト3秒。性能測定に基づく最適値ではなく、現時点の実装値。
- 通常参照はReplica。Primary用のGo接続設定はコメントアウトで、まだ利用していない。

## DB接続の残作業と検証範囲

- Ping失敗時にConnectDB内でdb.Close()する。成功時はmainのdeferで閉じる。
- 接続テストはrequire.NoError等で接続失敗時に停止し、nilのDBをCloseしない。テスト内のlog.Fatalfはt.Fatal等に替える。
- Goはsrc/.envのREAD_DB_*、Compose・接続確認スクリプトはルート.envのDB_READ_* / DB_WRITE_* / DB_NAMEを使用中。設定が二重化している。統一するか、用途別に維持して対応関係を明記するかは残作業。現状の読み込み位置は[環境手順](../infra/mysql/README.md)を参照。
- 2026-10-22の修正後レビューでgo test -count=1 ./...とgo vet ./...が成功。usersのSELECT、NewRouter経由の/demo-usersの200応答、JSONの5件・正のIDを確認。
- Request.ContextはPrepareContext / QueryContextまで伝播済み。ただし明示的なSELECTの期限は未設定。リクエストのcontextだけでは自動で3秒等のタイムアウトは付かない。
- 空設定・不正ポートのテストはある。明示的な設定値検証、タイムアウト発生の検証は未実装。

## デモユーザー取得の現在仕様

GET /demo-usersはusersからORDER BY RAND() LIMIT 5でIDを取得し、200で `{"users":[{"UserID":123}]}` を返す。取得失敗は500。現在のJSONキーはUserIDで、今回のリファクタリングでは変更しない。

現在の投入データはusers 148,065人全員に視聴記録があり、視聴なしは0人と実DBで確認済み。そのため現段階ではEXISTSを省略する。元データを変えて再投入するとusersが残るため、対象条件を再検証する。RAND方式は採用中だが、性能測定による評価は未完了。

0件時は現実装ではusers:null。空配列にするかは別途決め、今回の構造変更と混ぜない。

## 次の課題：struct・interfaceへのリファクタリング

Goコードは本人が実装する。APIのパス・JSON・取得条件を保ったまま、以下の順で進める。

1. repositoryにUserRepository structを作り、非公開のreadDB *sql.DBを保持する。NewUserRepository(readDB)で受け取る。接続の生成・Closeは引き続きmainの責務。
2. GetDemoUsers(ctx)をUserRepositoryのメソッドへ移す。DBを毎回引数で渡さず、保持したreadDBを使う。
3. 使用側のhandlerにDemoUserReader interfaceを定義する。契約はGetDemoUsers(context.Context) ([]repository.DemoUserID, error)。戻り値の型は当面既存のものを使い、大規模なパッケージ分割はしない。
4. UserHandler structにDemoUserReaderを持たせ、NewUserHandler(reader)で受け取る。HTTP処理をメソッドへ移す。
5. mainでrepository → handlerを組み立て、NewRouterへhandlerを渡す。router・handlerからsql.DBへの依存を外す。
6. テスト用structにも同じメソッドを実装し、DBなしで正常系・取得失敗時の500を検証する。実DBの統合テストは残す。

完了条件：同じ/demo-usersが動き、go test -short ./...でDBなしのハンドラーテストが通り、実DB統合テストも通る。interfaceを満たすための明示的なimplements宣言は不要。

期限付きcontextの追加も未対応として残す。キャンセル伝播とタイムアウトを区別して確認する。完了後は指定ユーザーの視聴作品・ジャンル取得へ進む。

## まだ決めていないこと

- 業務APIの確定パスとJSON形式、エラーのHTTPステータス。不正ID・不存在ID・同一ユーザー指定の扱い。
- 共通作品・ジャンルの上限、順序、ページング。デモユーザーは現在ランダム最大5件・ページングなし。
- 後続の業務方式を比較するinterfaceの対象。直近は上記のDemoUserReaderでDB実装とテスト用実装を差し替える。
- 紹介候補のランダム抽出方式。デモユーザーのRAND方式は実データで計測して評価する。

未決事項は対象のAPIへ着手するときに決める。確定した内容は実装方針とリクエスト例へ反映する。

## 更新・レビューの進め方

- 小さい単位で実装し、対象となる行の状態と検証結果を更新する。
- 「コードを書いた」「ローカルで実行した」「実データで確認した」を分けて記録する。
- ルールを変更したら実装方針を更新し、変更理由も残す。
- 調査時点の数値・検証結果は履歴として残し、最新の状態と混同しない。
